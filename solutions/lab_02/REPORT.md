### 2.1. Эксперимент A. Неизменяемый объект (`int`)
**Код эксперимента:**
```python
a = 10
b = a
print(a, b)
print(id(a), id(b))

a += 1

print(a, b)
print(id(a), id(b))
```

* **Ожидаемый результат (прогноз):**  
  До инкремента имена `a` и `b` ссылаются на один и тот же синглтон/объект числа `10` в пуле малых целых чисел (`id(a) == id(b)`). Операция `a += 1` для неизменяемого типа `int` эквивалентна `a = a + 1`: создается новый объект `11`, и имя `a` связывается с ним. Имя `b` продолжит ссылаться на исходный объект `10`.
* **Фактический результат:**
  ```text
  До изменения:     a = 10, b = 10
  Идентификаторы:   id(a) = 4321538296, id(b) = 4321538296
  a is b:           True
  После a += 1:     a = 11, b = 10
  Идентификаторы:   id(a) = 4321538328, id(b) = 4321538296
  a is b:           False
  ```
* **Объяснение:**  
  В Python переменные - это не ячейки памяти, а имена-указатели на объекты в куче. Поскольку целые числа (`int`) неизменяемы, изменить значение по адресу `4321538296` невозможно. Сложение порождает новый объект по адресу `4321538328`, на который перенаправляется ссылка `a`. Объект `10`, связанный с именем `b`, остается неизменным.

### 2.2. Эксперимент B. Изменяемый объект (`list`)
**Код эксперимента:**
```python
first = [10, 20]
second = first
second.append(30)

# Дополнительные действия:
second = [10, 20, 30]  # переназначение на новый список
print(first == second) # True
print(first is second) # False
second.append(40)
```

* **Ожидаемый результат (прогноз):**  
  Оператор `second = first` не копирует список, а создает псевдоним: оба имени ссылаются на один список в памяти. Вызов метода `second.append(30)` модифицирует сам объект на месте, поэтому `first` также изменится на `[10, 20, 30]`.  
  После переназначения `second = [10, 20, 30]` создается независимый объект списка с тем же содержимым: `first == second` вернет `True`, но `first is second` вернет `False` (разные адреса). Последующий `second.append(40)` никак не затронет `first`.
* **Фактический результат:**
  ```text
  До изменения:       first = [10, 20], second = [10, 20]
  Идентификаторы:     id(first) = 4300933824, id(second) = 4300933824
  После append(30):   first = [10, 20, 30], second = [10, 20, 30]
  Идентификаторы:     id(first) = 4300933824, id(second) = 4300933824

  После переназначения second = [10, 20, 30]:
  id(first) = 4300933824, id(second) = 4301661568
  first == second: True
  first is second: False
  После second.append(40):
    first  = [10, 20, 30]
    second = [10, 20, 30, 40]
  ```

**Схема 1. До переназначения:**

### 2.4. Ответы на вопросы для анализа (Задание 1)

1. **Меняет ли присваивание `second = first` сам объект?**  
   *Ответ:* Нет, операция присваивания связывает имя в текущем пространстве имен с существующим объектом в памяти. Сам объект не модифицируется, меняется лишь счетчик ссылок на него (увеличивается на единицу).
2. **Почему операция над неизменяемым объектом приводит к связыванию имени с другим объектом?**  
   *Ответ:* Неизменяемые объекты (`int`, `float`, `str`, `tuple`, `frozenset`) не имеют методов изменения внутреннего состояния на месте. Любая операция над ними (сложение, конкатенация) возвращает ссылку на вновь сконструированный объект. Поэтому оператор `+=` перепривязывает имя к этому новому объекту.
3. **Как определить, что два имени обозначают один объект?**  
   *Ответ:* С помощью оператора проверки идентичности `is` (например, `a is b`), который эквивалентен сравнению адресов объектов в памяти: `id(a) == id(b)`. В отличие от него, оператор `==` вызывает метод `__eq__` и сравнивает равенство значений по содержимому.

### 3.1. Исследование вариантов копирования структуры данных
Исходная структура:
```python
original = [
    ["Python", 5],
    ["Algorithms", 4],

alias = original
shallow = original.copy()
```

**Последовательность мутаций:**
1. `original.append(["Databases", 5])` - добавление нового элемента верхнего уровня.
2. `original[0][1] = 3` - изменение элемента во вложенном списке.

**Результаты идентификации объектов:**
* `id(original)` совпадает с `id(alias)`.
* `id(shallow)` и `id(deep)` - новые уникальные внешние списки.
* При вызове `original.append(...)` изменились только `original` и `alias`. В `shallow` и `deep` длина осталась равной 2.
* При вызове `original[0][1] = 3` оценка изменилась в `original`, `alias` и `shallow`, поскольку `shallow[0]` ссылается на тот же самый вложенный список `id: 4308110016`. В структуре `deep` осталась неизменной оценка `5`, так как глубокая копия рекурсивно клонировала вложенные списки (`id: 4308794496`).

#### Таблица наблюдений:

| Операция | Новый внешний объект | Новые вложенные объекты | Изменения независимы |
|---|:---:|:---:|---|
| **Присваивание (`alias`)** | **Нет** (тот же `id`) | **Нет** (те же `id`) | **Нет** (полная взаимная зависимость) |
| **Поверхностная копия (`shallow`)** | **Да** (новый `id`) | **Нет** (те же `id`) | **Частично** (независимы только операции добавления/удаления элементов в корневой список) |
| **Глубокая копия (`deep`)** | **Да** (новый `id`) | **Да** (новые `id`) | **Да** (полная изоляция на всех уровнях вложенности) |

### 3.2. Исследование ошибочного создания матрицы
При создании матрицы конструкцией:
```python
wrong_matrix = [[0] * 3] * 3
wrong_matrix[0][0] = 1
```
Фактический результат: `[[1, 0, 0], [1, 0, 0], [1, 0, 0]]`.  
Причина: оператор `* 3` дублирует *ссылки* на один и тот же список `[0, 0, 0]`. Идентификаторы всех строк матрицы идентичны (`id(row[0]) == id(row[1]) == id(row[2])`).

При корректном создании через списковое включение (list comprehension):
```python
correct_matrix = [[0] * 3 for _ in range(3)]
correct_matrix[0][0] = 1
```
Фактический результат: `[[1, 0, 0], [0, 0, 0], [0, 0, 0]]`.  
Причина: генератор `for _ in range(3)` на каждой итерации заново вычисляет выражение `[0] * 3`, создавая три независимых объекта-списка с уникальными идентификаторами памяти.

### 3.3. Ответы на вопросы для анализа (Задание 2)

1. **Чем поверхностная копия отличается от глубокой?**  
   *Ответ:* Поверхностная копия создает новый внешний контейнер, но элементы внутри него копируются лишь по ссылке (shallow). Глубокая копия рекурсивно обходит всю структуру объектов и создает дубликаты всех вложенных изменяемых объектов, сохраняя внутреннюю топологию связей и защищая от зацикливания.
2. **Почему глубокое копирование не следует применять автоматически ко всем объектам?**  
   *Ответ:* 
   **Высокие накладные расходы:** Рекурсивный обход структур и ведение словаря посещенных объектов `memo` существенно снижают производительность (в десятки и сотни раз медленнее поверхностного копирования) и повышают расход памяти.

3. **В каких случаях достаточно поверхностной копии?**  
   *Ответ:* Поверхностная копия достаточна, если:
   - Коллекция одномерна (содержит только неизменяемые типы: числа, строки, кортежи из скаляров);
   - Требуется изменить порядок элементов (сортировка), профильтровать список или добавить новые элементы верхнего уровня без изменения существующих вложенных данных.

## 4. Задание 3. Подсчет ссылок и время жизни объекта (`task_3.py`)

### 4.1. Исследование счетчика ссылок (`sys.getrefcount`)
Код:
```python
data = [1, 2, 3]
alias = data
container = [data]
del alias
container.clear()
```

**Фактическая динамика счетчика ссылок:**
* После `data = [1, 2, 3]`: базовый счетчик $N$.
* После `alias = data`: счетчик равен $N + 1$ (добавление новой ссылки).
* После `container = [data]`: счетчик равен $N + 2$ (внутренний массив списка хранит указатель на `data`).
* После `del alias`: счетчик равен $N + 1$ (уничтожение связывания имени `alias`).
* После `container.clear()`: счетчик возвращается к $N$ (очистка списка удаляет указатели).

**Объяснения ключевых механизмов:**
* **Временная ссылка `sys.getrefcount()`:** Функция принимает объект как аргумент `sys.getrefcount(obj)`. При передаче по значению создается временный локальный указатель, что увеличивает счетчик на 1 на время выполнения замера.
* **Инструкции, увеличивающие счетчик ссылок:** Присваивание новому имени (`b = a`), передача аргументом в функцию, добавление в коллекцию (`list.append`, `dict[...] = ...`).
* **Инструкции, уменьшающие счетчик ссылок:** Удаление имени командой `del`, перепривязка переменной к другому объекту, удаление элемента из контейнера (`pop`, `remove`, `clear`), завершение выполнения функции.
* **Суть команды `del alias`:** Команда `del` не вызывает напрямую функцию деструкции объекта в памяти. Она лишь удаляет привязку имени `alias` из соответствующего пространства имен и уменьшает внутреннее поле объекта. Уничтожение объекта происходит автоматически только тогда, когда достигает нуля.

### 4.2. Слабые ссылки (`weakref`) и практическая задача
Слабые ссылки (`weakref.ref`) позволяют ссылаться на объект, не увеличивая счетчик `ob_refcnt`.

**Результаты практической задачи с `WeakValueDictionary`:**
1. В слабом словаре зарегистрированы три объекта: `user1`, `user2`, `user3`. На объект `user3` существовала только временная переменная `temp_r3`.
2. После вызова `del temp_r3` объект `Record` немедленно уничтожается сборщиком, и ключ `"user3"` автоматически удаляется из словаря `registry`.
3. После вызова `del r1` аналогично очищается ключ `"user1"`.
4. В реестре остался только `"user2"`, на который сохраняется сильная ссылка `r2`.

**Применение слабых ссылок в реальной разработке:**
- **Кэширование данных (Cache / Memoization):** Хранение тяжелых объектов (например, загруженных текстур или моделей), которые автоматически выгружаются из памяти, если приложение больше не использует их в активной логике.

### 4.3. Ответы на вопросы для анализа (Задание 3)

1. **При каком условии подсчет ссылок позволяет освободить объект?**  
   *Ответ:* Объект немедленно уничтожается, как только счетчик сильных ссылок (`ob_refcnt`) становится равным строго 0.
2. **Всегда ли освобождение Python-объекта означает немедленный возврат памяти операционной системе?**  
   *Ответ:* Нет. Для оптимизации быстродействия CPython использует собственный менеджер памяти `PyMalloc` (для объектов размером до 512 байт). Память запрашивается у ОС крупными блоками (аренами по 256 КБ). При уничтожении объекта память возвращается в локальный пул `PyMalloc` для повторного переиспользования Python-объектами, а физический возврат ОС (вызовы `free`/`munmap`) происходит только при полном освобождении всей арены.
3. **Чем сильная ссылка отличается от слабой?**  
   *Ответ:* Сильная ссылка инкрементирует счетчик `ob_refcnt` объекта и удерживает его от удаления. Слабая ссылка (`weakref`) регистрируется в специальном двусвязном списке объекта, не увеличивает `ob_refcnt` и возвращает `None`, как только объект освобождается.

### 5.1. Эксперимент с циклическими ссылками
Код:
```python
first = []
second = []
first.append(second)
second.append(first)
del first, second
collected = gc.collect()
```

* **Ожидание:** После `del first, second` оба списка взаимно ссылаются друг на друга. Счетчик ссылок каждого списка равен 1, но из корней программы (глобальной/локальной области видимости) они недостижимы. Подсчет ссылок не может их удалить. Вызов `gc.collect()` обнаружит цикл и освободит оба объекта.
* **Фактический результат:**
  ```text
  first ссылается на second: True
  second ссылается на first: True
  Вызов gc.collect() вернул: 2
  ```

### 5.2. Поколения сборщика мусора и эксперимент при отключенном GC
* **Пороги сборщика:** `gc.get_threshold() = (2000, 10, 10)`.
* **Принцип поколений (Generational Hypothesis):**  
  Сборщик мусора CPython разделяет контейнерные объекты на 3 поколения (0, 1, 2). В основе лежит эмпирическая гипотеза о том, что большинство объектов «умирают молодыми» (временные переменные внутри функций). Поколение 0 проверяется чаще всего. Объекты, пережившие сборку мусора, переходят в поколение 1, а затем в поколение 2 (долгоживущие). Это предотвращает затратное полное сканирование всех объектов программы на каждый шаг сборки.
* **Эксперимент с `gc.disable()`:**
  При отключенном автоматическом GC было создано 5 изолированных циклических пар списков. Внутренний счетчик поколения вырос, память оставалась неосвобожденной. После ручного вызова `gc.collect()` сборщик мусора успешно очистил все 10 циклических объектов. Автоматический режим был восстановлен через `gc.enable()`.

### 5.4. Ответы на вопросы для анализа (Задание 4)

1. **Как возникает циклическая ссылка?**

2. **Почему объект с ненулевым счетчиком ссылок иногда может быть недостижим из программы?**

Такая структура становится недостижимой, но механизм подсчета ссылок не способен распознать изолированность цикла.
3. **Зачем сборщик мусора разделяет отслеживаемые объекты по поколениям?**  
   *Ответ:* Для оптимизации работы, для сокращения объектов, которые не используются.

### 6.1. Размер базовых объектов в памяти CPython (`sys.getsizeof`)

| Объект                    | Выражение в коде                  | Размер в байтах |
| ------------------------- | --------------------------------- | :-------------: |
| **Объект `None`**         | `sys.getsizeof(None)`             |    **16 Б**     |
| **Целое число `10`**      | `sys.getsizeof(10)`               |    **28 Б**     |
| **Строка из 10 символов** | `sys.getsizeof("0123456789")`     |    **51 Б**     |
| **Пустой список**         | `sys.getsizeof([])`               |    **56 Б**     |
| **Кортеж из 10 чисел**    | `sys.getsizeof(tuple(range(10)))` |    **128 Б**    |
| **Список из 10 чисел**    | `sys.getsizeof(list(range(10)))`  |    **136 Б**    |

> **Почему `sys.getsizeof()` не включает полный размер вложенных объектов?**  
> Контейнеры в Python являются коллекциями указателей. В структуре списка физически хранятся только 8-байтные C-указатели. Сами данные (объекты `int`, строки и т.д.) лежат в других областях кучи. Поэтому `sys.getsizeof(list)` возвращает поверхностный размер (shallow size) самого массива указателей.

### 6.4. Итоговый анализ: 3 способа снижения расхода памяти
3 ключевых метода оптимизации на основе проведенных экспериментов:

Своевременное обнуление ссылок или использование слабых обратных ссылок в графовых структурах избавляет циклический сборщик мусора от необходимости накапливать недостижимые циклы.

## 7. Итоговый вывод о наиболее опасных ошибках при работе с изменяемыми объектами

В ходе выполнения лабораторной работы были экспериментально исследованы ключевые ловушки ссылочной модели Python:

1. **Ошибочное использование псевдонимов вместо копирования**
2. **Использование поверхностного копирования для многомерных структур**
3. **Создание матриц и списков через умножение:** Конструкция вида `[[0] * N] * M` создает $M$ ссылок на один и тот же вложенный список, превращая любую модификацию ячейки в одновременное изменение всех строк. Правильный паттерн - списковое включение `[[0] * N for _ in range(M)]`.
4. **Непреднамеренное удержание объектов в памяти через локальные переменные и циклы:** Как показал эксперимент с `WeakValueDictionary`, переменные циклов `for` сохраняются в локальной области видимости функции после завершения цикла, продолжая удерживать сильные ссылки на объекты и мешая их своевременному завершению.
5. **Замкнутые циклические ссылки при отключенном или перегруженном GC:** Циклические ссылки не могут быть удалены стандартным механизмом подсчета ссылок и накапливаются до вызова `gc.collect()`, что при высоких нагрузках приводит к неконтролируемым утечкам памяти.
